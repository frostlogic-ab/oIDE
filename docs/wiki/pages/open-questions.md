# Open questions and risks

The build brief's table ([raw/build-brief.md](../raw/build-brief.md), "Open questions and risks") with a
**Finding** column. Findings for questions 2, 4, 6, 7, 8, 9 and 10 come from real CLI 2.1.325 sessions on
2026-11-24; details in [cli-integration](cli-integration.md) and [subagents](subagents.md).

| # | Question or risk | Default until answered | Finding |
| --- | --- | --- | --- |
| 1 | Does Anthropic accept oIDE driving the user's own CLI, many sessions at once, on a Pro or Max plan? | Build as designed; ask before any public release; API-key mode as a fallback | Open (needs the maintainer to ask Anthropic). Blocks a public release. |
| 2 | Is stream-json stable enough, and which control messages (mode change, interrupt) are supported? | Pin a tested range, parse in one package, weekly fixture diff | **Answered for 2.1.325.** `control_request` `interrupt` and `set_permission_mode` both work and return `control_response` `success` (`{still_queued:[]}` / `{mode}`); the mode change is echoed as `system/status {permissionMode}`. Fallbacks (SIGINT, interrupt + `--resume`) are implemented and tested against fake-claude. The format carries many fields oIDE ignores; the parser keeps unknown types as `unknown` events. |
| 3 | Raw CLI or the Agent SDK pointed at the user's binary? | Raw CLI behind `AgentDriver` | Raw CLI shipped (`ClaudeCliDriver`). Open until question 1. |
| 4 | Where do plan usage percentages and reset times come from? | Tokens per agent and rate-limit reset times; hide meters | **New source found:** every turn emits `rate_limit_event.rate_limit_info` with `status`, `resetsAt`, `rateLimitType` (`seven_day`, …) and `unifiedWindows.<window>.utilization` (0.65 = 65%). Surfaced as `plan-usage` events and `AgentSummary.planUsage`. Only the window the CLI reports is known (one at a time), so a full Session/Week pair may not always be available. |
| 5 | Is there an API or connector for claude.ai artifacts? | Local artifacts plus manual import | **Answered ([ADR 0014](../../adr/0014-multi-file-artifacts-retrieved-by-agents.md)).** No public API, and oIDE itself never downloads claude.ai content. A pasted link creates the artifact at version 0 and starts an ordinary agent (the user's own `claude` CLI) that reads it with whatever claude.ai tools the CLI has (an Artifact tool when there is one, the Claude Docs connector, `DesignSync` for claude.ai/design projects) and hands the files back with `artifact_retrieval_add_files` / `artifact_retrieval_finish`; Update repeats it. CLI 2.1.332 has no tool that reads `/artifact/<id>` Design links, so those fail with the agent's reason until it gets one. See [artifacts.md](artifacts.md). |
| 6 | Exact names for Auto mode, effort level and subagent model settings | Detect from `--help`, hide what is missing | **Auto:** `--permission-mode auto` (accepted, init reports `auto`). Help lists `manual` instead of `default`; `default` is still accepted. New mode `dontAsk`. **Effort:** `--effort low|medium|high|xhigh|max` (per session). **Subagent model:** `CLAUDE_CODE_SUBAGENT_MODEL` env var (not verified in a session); `--agents` definitions take a `model` per subagent (verified). |
| 7 | Does `/compact` work when sent through stream-json input? | Tell the user to compact in the Raw terminal | **Yes.** A user message with content `"/compact"` compacts (status `compacting`, `compact_boundary` with pre/post tokens, `result` with `local_command:"compact"`). |
| 8 | Do subagent events, usage and permission prompts carry the parent Task id? | Show subagents from Task calls and results only | **Yes for events and usage** with `--forward-subagent-text`: subagent `assistant`/`user` lines (text, tool_use, tool_result, usage) carry `parent_tool_use_id` = the lead's `Agent` tool_use id. **Permission prompts** carry only the subagent's own `tool_use_id`, which oIDE maps to the subagent via its tagged tool_use. Also: the tool is now `Agent` (not `Task`), subagents may run **async** (the lead's turn ends first; the report arrives in `system/task_notification.summary`), and `system/task_*` events give start, progress, end and total tokens. |
| 9 | Can one subagent be stopped on its own? | Deny its next tool call with a stop message; otherwise hide the button | No control message found for it. Implemented the default: `stopSubagent` denies the subagent's pending and next prompts with a stop message. It only bites when the subagent's next tool needs a prompt (not for auto-allowed tools such as Read). |
| 10 | Per-subagent effort in `--agents` definitions | Effort on the lead only, tiers labelled by model | `effort` inside an `--agents` definition is accepted without error, but nothing in the stream shows whether it is applied. oIDE passes it and labels it unverified. |
| 11 | Plan limits with 6+ agents and their subagents | Max running 3, queue, clear limit errors, subagent token share | Implemented: queue with `maxRunning`, `rate-limited` status with reset time and no retry, `subagentTokenShare()`. |
| 12 | Extension and custom-tool sandboxing | Consent dialog, no install scripts, hash check | **Implemented as the default**: first-run consent dialog (tools, capabilities, commands), no install scripts, tarball `integrity` checked (`packages/extension-host/src/integrity.ts`), host code in a separate utility process, UI in sandboxed `oide-ext://` iframes, secrets scoped per extension. **Not a sandbox** (SEC-14): the utility process has full Node, so declared capabilities (`network`, `spawn`) are consent text, not enforced; stdio servers and custom local commands run with the user's rights after consent. Still open: real enforcement. |
| 13 | Remote MCP servers without dynamic client registration | Paste a client id or a header token | **Implemented as the default** in Add custom: OAuth with dynamic client registration, or a pasted client id (`packages/extension-host/src/oauth.ts`), or a header token; tokens stay in main and reach the server through the per-agent MCP proxy (`mcp-proxy.ts`). |
| 14 | Code signing accounts and costs | Unsigned betas | Open (needs the maintainer's accounts). Release CI signs only when the secrets exist ([packaging](packaging.md)); until then builds are unsigned. |
| 15 | Licence and name check | Apache-2.0 (guess) | **Licence:** MIT (see LICENSE). **Name check (2026-11-24, nothing registered):** npm package `oide` is unregistered (registry 404), and so are the scopes `@oide-dev` and `@oide-community`. **The npm scope `@oide` is taken**: org `oide` publishes `@oide/edio-test-package` (2024-10-07, an unrelated maintainer), so `@oide/extension-api` cannot be published as named. **Open decision (maintainer):** claim a free scope (proposal: `@oide-dev`, matching the GitHub org) and rename the published package, or ask the `@oide` owner to transfer the scope. Until it is decided, nothing is published to npm and no doc should tell anyone to install or publish under `@oide`; package names in the repo stay as they are. The bundled marketplace index names `@oide/ext-*` tarballs on registry.npmjs.org, pinned by `integrity`, so a package someone else publishes there fails the hash check rather than installing. GitHub: `oide-dev` is free (users/orgs API 404, matches `publish.owner` in electron-builder.yml); `oide` is a dormant personal account (2011, 0 public repos). Similar names on GitHub are small and unrelated: `springhack/Android_OIDE` (an IDE for competitive programmers on Android, 11 stars), `zakhaev26/OiDE-compiler`; on itch.io `o.ide`, an Amstrad CPC text editor. Outside software, **Oide** is Ireland's Department of Education support service for teachers (oide.ie, since 2023); different field, but it owns the plain-word web presence. No registered "OIDE" software trademark turned up in a web search; a USPTO/EUIPO search by a person is still needed before 1.0. |
| 16 | Whiteboard library licence | Excalidraw | **Decided: Excalidraw** (`@excalidraw/excalidraw` 0.18, MIT), embedded as the whiteboard editor ([screen-artifacts](screen-artifacts.md)). Its bundled fonts (Virgil, Excalifont, Xiaolai and others) ship in the renderer; their licences need listing in the third-party notices. |
| 17 | May CI use a maintainer's own subscription sign-in? (nightly real-CLI smoke, weekly scripted compat session) | Off: `nightly-real-cli.yml` and the `session` job of `cli-compat.yml` run only when the repo variables `OIDE_NIGHTLY_REAL_CLI` / `OIDE_CLI_COMPAT_SESSION` are `true`, on a self-hosted runner labelled `oide-real-cli` | Open; part of question 1 to Anthropic (the brief marks it a guess). The hosted weekly job needs no sign-in (`--version`, `--help`, flag detection). Fallback if subscription use is not allowed: an API-key runner whose key lives only in the runner's own environment. |
| 18 | Trademark for the oIDE name and logo; trademark policy for forks | Logo and name ship under MIT with the code; no registration, no policy | Open (maintainer). MIT covers copyright, not trademark. Needs: a USPTO/EUIPO search for "oIDE" and the Signal mark ([docs/brand](../../brand/README.md)) before 1.0, a decision on registering, and a short policy (e.g. forks keep the code but drop the name and logo). |
| 19 | Does each `CLAUDE_CONFIG_DIR` get its own macOS keychain entry? ([claude-accounts](claude-accounts.md)) | Assumed yes; not verified | Open. On macOS the CLI keeps credentials in the keychain, not in the folder. Check it on a Mac for each tested CLI version: sign in to two accounts, then run an agent on each and look for an `init` on both. If the entries are shared, mark accounts as Windows and Linux only. |
| 20 | Running several of one person's own Claude plans from one oIDE | Allowed when the user picks the account per agent; never automatic failover between accounts | Part of question 1 to Anthropic. oIDE never moves work to another account when one hits its limit, and never picks the least-used account by itself ([ADR 0021](../../adr/0021-several-claude-code-accounts.md)). |
